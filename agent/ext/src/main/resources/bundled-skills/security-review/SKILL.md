# /security-review

对当前分支相对默认分支的改动做一次性的安全审查。它是一次按需的单趟审查；回合末与提交后的自动审查见 security-guidance（在 settings 的 `enabledPlugins` 里启用），整个仓库的深度扫描不在这里做。

## 步骤

1. 确定范围：优先用当前分支与 `origin` 默认分支的差异（`git diff origin/HEAD...`）。没有 `origin` 远程或取不到它的默认分支时，改用与本地 `main` / `master` 的合并基点，再不行就用 `HEAD` 之后未提交的改动；说明你用的是哪一种。给了分支或路径参数时，只看那一部分。
2. 读改动，也读它周围的代码：调用者、输入从哪来、有没有校验或转义，再判断一个看着危险的写法是否真的能被不可信输入触到。
3. 重点找这几类：
   - 注入：SQL、命令、模板、路径穿越；
   - 认证与授权：缺少校验、可绕过的检查、越权访问他人数据；
   - 服务端请求伪造、不安全的反序列化、不转义的 HTML / DOM 写入；
   - 密码学误用：写死的密钥、可预测的随机数、非常量时间比较密钥；
   - 数据暴露：把凭证或个人数据写进日志、响应或源码；
   - 过宽的 CI / 云权限。
4. 每条发现要说得清「谁能提供什么输入、走哪条路径、造成什么后果」。猜测、风格问题、只在理论上存在的风险不报。
5. 有发现时，调用 `ReportFindings` 工具一次交上全部发现：`file`、`summary`、`failure_scenario`（攻击场景）、能确定时填 `line`，`category` 填 `security`，`severity` 用 `important`（合并前应修）、`nit`、`pre_existing`（原本就有）。
6. 没有发现时，直接说「没有发现安全问题」并列出审查了哪些文件，不要调用 `ReportFindings`。
7. 最后一两句话概括：几条、哪几条最要紧、哪些地方你没有能力判断（比如依赖运行环境配置的）。

## 边界

- 只审改动，不改代码；要改，由用户决定后再动手。
- 审查的是源码，不是正在运行的服务。
