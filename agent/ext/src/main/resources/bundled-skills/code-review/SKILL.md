# /code-review

审查改动，找出会导致错误的正确性问题。

## 参数

- 努力档：`low`、`medium`、`high`、`xhigh`、`max`，缺省用会话当前的档位。`low` 只报最有把握的几条；从 `medium` 起逐步扩大覆盖面，`max` 最宽。
- `--fix`：审查之后把发现的问题直接改进工作区。改完逐条说明：修了、跳过了（说明理由），还是经核实不需要改。
- `--comment`：把发现作为行内评论发到 GitHub PR。Min 没有 GitHub 集成，本环境里这个参数不可用：告诉用户，结果照常在对话里给出，不要假装已经发了评论。
- 目标：`PR号`（用 `gh` 取得 diff，如果可用）、分支名（与默认分支比较）、文件或目录路径。都不给时，审查当前分支相对上游的提交，加上未提交的改动。

## 步骤

1. 确定范围：用 `git` 取 diff。目标含糊时先问用户。
2. 读改动以及它周围的代码，不只看 diff 的几行。
3. 对每个怀疑的问题做核实：能说清具体的失败场景（什么输入、走哪条路径、会得到什么错误结果）才算发现。只是风格偏好、猜测、或测试覆盖不足的，不报。
4. 有发现时，调用 `ReportFindings` 工具一次交上全部发现。每条填：
   - `file`：文件路径；
   - `summary`：一句话说明问题；
   - `failure_scenario`：在什么情况下会出错；
   - `line`：能确定行号时填；
   - `category`：如 `correctness`；
   - `severity`：`important`（合并前应修）、`nit`（小问题，值得修但不阻塞）、`pre_existing`（代码里原本就有，不是这次引入的）。
5. 没有发现时，直接说「没有发现正确性问题」并列出审查了哪些文件，不要调用 `ReportFindings`（它要求至少一条）。
6. 带了 `--fix` 时，在交上发现之后修改代码，并重新跑相关的测试。
7. 最后用一两句话概括：几条、哪几条最要紧、做了什么改动。

## 边界

- 本 skill 只找正确性问题。简化与复用的清理归 `/simplify`。
- 不修改与改动无关的文件。
