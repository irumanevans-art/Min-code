# 06 · 路线图

原则：**先在桌面 JVM 上把内核做对，再进 App**；每个里程碑有可量化的验收门槛，不过门不进下一个；
CLI 引擎全程可用，任何时候用户都能切回去。每个里程碑结束发一版（按发版节奏，一个会话最多一版）。

分工记号：**[O]** Opus（判断、并发、架构、安全、观感）；**[G]** GLM 5.3 Flash（机械、行为等价、可被测试或 grep 验证）。

---

## M0 · 基线与脚手架

**为什么先做**：仓库里没有 proot 性能、phantom process killer、CLI 冷启动的实测数据，没有基线就说不清「自研省了多少」；
模块边界要在第一行业务代码之前立起来。

| 交付 | 谁 |
|---|---|
| 基线测量脚本 + 报告：CLI 冷启动到首 token、每会话 PSS、proot 内 `rg` / `find` / `git status` 耗时 vs 宿主侧同操作、phantom 进程行为、FGS 下 Doze 联网 | [G] 按脚本跑，[O] 解读 |
| 真机验证 4 项：musl 静态 rg 能否在 App 进程直接执行、sqlite FTS5 可用性、ktreesitter + bash 语法 .so 体积、持 FGS 进程 Doze 下网络 | [G] 跑，[O] 判 |
| `agent/` 下 11 个模块骨架、依赖规则架构测试、`catchingNonCancellation` 与禁用 `runCatching` 挂起调用的检查 | [G] 按 02 §2 搭，[O] 审 |
| `:agent:protocol` 与 `:agent:spi` 的类型定义（照 03 草图） | [O] 定稿，[G] 补序列化与往返测试 |
| `agent/store/FORMAT.md`、每个模块 README 模板 | [G] |

**门槛**：`./gradlew :agent:kernel:test` 绿；架构测试能拦住故意写错的依赖；基线报告有数。

## 风险与对策

| 风险 | 对策 |
|---|---|
| 对标面太大，又做出一个半成品 | 05 清单是唯一验收依据；每个里程碑只收门槛内的项；CLI 引擎全程兜底 |
| 进程内内核跟 App 一起被杀 | 日志即真相 + 恢复混沌测试是 M1 门槛，不是后补 |
| 安全闸门从 CLI 挪到 Min 自己身上 | 安全底线不可配置；一套命令解析器；安全相关改动必须 [O] 审且带用例 |
| 路径语义错了难排查 | PathMapper 独立、先写测试、越界一律拒 |
| 国产端点「兼容」但细节不同 | 怪癖表数据化 + 逐家夹具 + 评测；不支持就报错不降级 |
| 提示词改动造成隐性退化（CC 踩过） | 请求快照测试 + 评测集，改提示必过评测 |
| 巨型文件复辟（CC 循环体 1400 行、Codex 5000 行文件） | 800 行警戒线写进架构测试的告警 |
