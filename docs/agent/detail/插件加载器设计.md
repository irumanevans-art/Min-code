## 一、范围

插件 = 一个目录，里面可以放 skills、commands、agents、hooks、MCP 服务器、LSP 服务器、monitors、输出样式、主题；由 `plugin.json` 清单声明。本设计只管「装载与合并」：读清单、解析组件、算名字、合并进会话。**市场安装与第三方源的决定见 M5 总览的待定 1，这里不做。**

## 二、装载流程

1. **找候选**：`enabledPlugins`（合并后的设置，`plugin-name@marketplace-name` 为键；键里的 name / marketplace 先过字符集校验，拼出的路径必须仍在 `~/.claude/plugins/cache/` 下）+ `--plugin-dir` 指定的目录（id 为 `<name>@inline`，**替换同名的已装插件、只装一份**，记一条 override 说明；托管设置 `disableSideloadFlags` 可禁用旁加载）。（更正：初稿没写同名优先级与穿越校验）
2. **读清单**：**清单是可选的**（PLG:30；更正：初稿写成「不存在就记错误」）。存在但不是合法 JSON、顶层不是对象 → 该插件记一条错误，**不影响其他插件**（PLG:103–113 是 `validate` 命令报告的错误类别）。未知顶层键剥掉并照常装载（PLG:96，记入 `strippedUnknownTopLevel`）。
3. **校验**：字段类型、必填项、`name` 字符集（无清单时取来的目录名 / 条目名同样要过）；严格对象（PLG:324 等）错了就记错误、跳过该组件。错误一律**收集不抛出**，装载结果带 `errors` 列表；任何一个插件出错都不能让会话创建失败。
4. **解析组件路径**：默认目录（`skills/`、`commands/`、`agents/`、`hooks/hooks.json`、`.mcp.json`、`.lsp.json`、`output-styles/`、`themes/`、`monitors/`）与清单里写的路径合并。合并规则按原文 PLG:408–418「How each key combines with its default location」。路径三规则（PLG:392「必须以 `./` 开头」，PLG:399–404 包含与存在）：必须以 `./` 开头、不能逃出插件目录、必须存在；任一不满足就是该组件的错误，**插件照常装载、只缺这个组件**（CC 官方 plugins/loading「the plugin loads without that component」；更正：样本 17、19、22–24 原先要求整个插件装不上，与此不符，随修复单改样本）。三规则对**所有**路径形写法都适用，包括 `commands` 的对象形 `source`。超限 / 超深的普通文件不影响装载，只有声明过的组件文件读不了才算该组件的错；错误信息带文件路径。
5. **算名字**：命名空间 `<插件>:<名字>`（原文 CMP:662、724、930）。插件名：有清单就用清单的 `name`（PLG:127，必填）；没有清单时，从市场装的取 marketplace 条目名、`--plugin-dir` 装的取目录名（PLG:30）。条目名与清单名不同时，`enabledPlugins` 用条目名、组件的命名空间用清单名（PLG:686）。`SKILL.md` 的 frontmatter `name` 只替换最后一段（CMP:662）。
6. **依赖**：被依赖的插件**只无视 `defaultEnabled`**（PLG:204）；正常设置优先级得出的**最终值为 false**时，依赖它的插件装载失败并报错「依赖 X 被禁用」。托管 false 不能被其他层覆盖；普通低层 false 被高层 true 覆盖后不再阻止依赖（官方 plugins/loading 的启用来源表与 plugins/dependencies）。循环依赖记错误、两边都不启用。
7. **同名覆盖**：两个插件设同一个 settings 键，后装载的赢（CMP:919，`--debug` 记 overrides）；两个 LSP 服务器认领同一扩展，先注册的接管（CMP:874）；`.mcp.json` / `.lsp.json` 先装载，清单声明的同名后到取代（PLG:305、322–323）。
8. **产出** `LoadedPlugin` 列表与 `errors`。失败的插件不进列表，但错误要能在界面看到。

## 四、信任：启用来源与安装作用域

插件的 hooks 与 MCP 服务器都能跑命令。信任轴照 CC 官方 plugins/loading 页：

- **个人插件由用户或托管层启用**：视为用户信任，hooks 与 MCP 照常启用。用户 true 与项目 true 同时存在时保留用户信任来源，最终启用值仍按普通设置优先级合并。
- **项目层或 local 层启用，或安装作用域为 project/local**：工作区被信任之后才装载**整个插件**；候选在读取组件前过滤，settings、skills、commands、agents、styles、hooks、MCP 均不进入会话。个人启用也不能豁免实际 project/local 安装作用域。`-p` 不算工作区信任。项目插件 MCP 服务器还需逐服务器审批。
- **`--plugin-dir`**：用户亲手旁加载，视同用户信任（不受 cwd 范围限制）。
- **受信的文件范围**只到 `~/.claude/plugins/cache/` 与索引里登记的 `installPath`；`marketplaces/`（市场的克隆）与 `data/`（插件可写的数据目录）不算受信位置。

初稿按「插件所在目录是否被信任」判，对市场插件几乎恒真（都落在用户目录的 cache 里），于是一个没被信任的仓库能在项目设置里启用你缓存里的插件并执行它的 hooks——复核端到端复现过。

## 五、敏感配置

`userConfig` 里 `sensitive: true` 的值（比如 API key）：

- **不写进 `settings.json`**（PLG:437、488 原文要求）。
- 存放位置与 MCP OAuth 令牌一致：Android 用 Keystore 加密文件，桌面用只给当前用户的文件（已有实现，见 `FileMcpTokenStore` / `AndroidMcpOAuth`）。不进 rootfs、不进会话日志、不进事件。
- 替换规则（更正）：`${user_config.KEY}` 在 MCP / LSP 配置与 exec-form hook 的 args 里替换成**真值**；`CLAUDE_PLUGIN_OPTION_<KEY>` 对每个选项导出给 hook。sensitive 的真值只经 spawn 时的**进程参数 / 环境变量**传，不写进 rootfs 里的脚本文本。skill / agent 正文里：非 sensitive 替换真值，sensitive 只替换成占位符文本。

## 六、变量替换

- `${CLAUDE_PLUGIN_ROOT}`、`${CLAUDE_PLUGIN_DATA}` 等环境变量：在使用侧替换（PLG:563–578 的解析规则），不在装载时替换。装载结果里保留原始 JSON。
- `${user_config.*}`（更正）：MCP / LSP 配置、exec-form hook 的 args、skill / agent 正文都会替换（规则见第五节）；**monitors 的命令里禁止引用**（PLG:388）。

## 七、测试与变异

- 样本：`plugin-compat` 46 个，实现时逐个摘 `pendingFix`。
- 契约映射：`PluginCompatTest` 已有探针断言「还没有 `PluginLoader`」，加载器落地那天它会红，提醒摘标记。
- 变异：对每条合并规则（同名覆盖、依赖拉起、三路径规则、严格对象）各做一个变异，对应样本应变红。
- 信任：未信任项目插件既无正文也不执行 hooks，个人插件仍执行 hooks 并能展开命令正文；分别用真实会话验证，另验证双层重复 true、最终 false 与托管 false。

## 九、决定补充（2026-10-08，用户确认）

- **官方市场默认开**：可以浏览和安装官方源的插件。
- **第三方源不默认开**：用户手动添加时弹明确警告（说明插件可能运行命令、可能访问网络）。
- 插件的 hooks 与 MCP 服务器按第四节的「启用来源」判信任（更正：初稿写的「所在目录被信任」是错的轴）。市场来源不改变这条规则。
