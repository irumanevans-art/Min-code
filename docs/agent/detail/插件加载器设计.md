# 插件加载器设计

日期：2026-10-08。状态：草案。依据：`PluginLoaderContract.kt`（测试源契约草案，`agent/ext/src/test/.../plugins/`）与 `plugin-compat` 46 个样本（全部待修，`agent/ext/src/test/resources/plugin-compat/`）。原文：CC `cc-plugins-reference.md`（PLG）、`cc-plugins-components.md`（CMP）、`cc-settings-reference.md`（SET）。

字段清单（清单字段、环境变量、组件目录）由 Haiku 整理到 `research/tasks/HAIKU_REPORT_2026-10-08_plugin-fields.md`，这份设计以它为准，有出入以原文为准。

## 一、范围

插件 = 一个目录，里面可以放 skills、commands、agents、hooks、MCP 服务器、LSP 服务器、monitors、输出样式、主题；由 `plugin.json` 清单声明。本设计只管「装载与合并」：读清单、解析组件、算名字、合并进会话。**市场安装与第三方源的决定见 M5 总览的待定 1，这里不做。**

## 二、装载流程

1. **找候选**：`enabledPlugins`（合并后的设置，`plugin-name@marketplace-name` 为键）+ `--plugin-dir` 指定的目录（没有 marketplace，名字取清单 name，再退到目录名）。
2. **读清单**：`plugin.json` 不存在、不是合法 JSON、顶层不是对象 → 该插件记一条错误，**不影响其他插件**（原文 PLG:111「装载时报同样的错」）。未知顶层键剥掉并照常装载（PLG:96，记入 `strippedUnknownTopLevel`）。
3. **校验**：字段类型、必填项、`name` 字符集；严格对象（PLG:324 等）错了就记错误、跳过该组件。错误一律**收集不抛出**，装载结果带 `errors` 列表。
4. **解析组件路径**：默认目录（`skills/`、`commands/`、`agents/`、`hooks/hooks.json`、`.mcp.json`、`.lsp.json`、`output-styles/`、`themes/`、`monitors/`）与清单里写的路径合并。合并规则按原文 PLG:408–418「How each key combines with its default location」。路径三规则（PLG:399–407）：必须以 `./` 开头、不能逃出插件目录、必须存在；任一不满足就是该组件的错误。
5. **算名字**：命名空间 `<插件>:<名字>`（原文 CMP:662、724、930）。插件的显示名来源顺序：清单 name → marketplace 条目名 → 目录名（PLG:30）。`SKILL.md` 的 frontmatter `name` 只替换最后一段（CMP:662）。
6. **依赖**：被依赖的插件无视 `defaultEnabled` 直接启用（PLG:204）。循环依赖记错误、两边都不启用。
7. **同名覆盖**：两个插件设同一个 settings 键，后装载的赢（CMP:919，`--debug` 记 overrides）；两个 LSP 服务器认领同一扩展，先注册的接管（CMP:874）；`.mcp.json` / `.lsp.json` 先装载，清单声明的同名后到取代（PLG:305、322–323）。
8. **产出** `LoadedPlugin` 列表与 `errors`。失败的插件不进列表，但错误要能在界面看到。

## 三、Min 里的落点

| 组件 | 接到 Min 的哪里 | 说明 |
|---|---|---|
| skills / commands | 现有的 `SkillDef` / `CommandDef` 装载路径，`source = plugin:<名字>` | 斜杠名 `/插件:名字`，与 skill 清单共用冻结快照机制 |
| agents | 现有子 agent 定义，名字 `插件:名字` | 子 agent 的工具限定照原有规则 |
| hooks | 现有 hook 引擎，层级新增 `plugin` | 见下面「信任」 |
| MCP 服务器 | `McpConfigLoader` 的一个来源，作用域 `plugin` | 服务器在 /mcp 里叫 `plugin:<插件>:<server>`，工具 `mcp__plugin_<插件>_<server>__<tool>`（CMP:824–825） |
| LSP | **本期不做**：Min 没有 LSP。清单里有 `lspServers` 的插件照装，LSP 部分记「未支持」 | 05 里 LSP 行是 M5 最后做的 |
| monitors | 依赖后台任务登记（M5 总览第 7 项），本期记「未支持」 | |
| 输出样式 / 主题 | 现有 output style 机制，名字 `插件:名字`；主题按文件里的 name，不带前缀（CMP:929） | |

## 四、信任（这是安全决定，需要你确认）

插件的 hooks 与 MCP 服务器都能跑命令。所以：

- **插件的 hooks 与 MCP 服务器只在「插件所在目录已被用户信任」时才启用**，和现有项目层 hooks 的信任规则同一套（工作区信任）。插件来自用户自己的 `~/.claude/plugins/`（用户层）时，视为用户信任。
- **装在项目目录里的插件（项目层）**：沿用项目层信任，未信任就不启用它的 hooks / MCP，并在界面提示。
- 这与 M5 总览待定 1 相关：第三方市场默认关。本设计假设插件只能来自用户层或项目层，市场安装另议。

**待你确认**：上面这条「插件 hooks / MCP 跟随工作区与用户信任」，我觉得是合理的最小方案，但它直接影响能不能跑插件里的命令。如果你要更严（插件 hooks 一律要单独批准），告诉我。

## 五、敏感配置

`userConfig` 里 `sensitive: true` 的值（比如 API key）：

- **不写进 `settings.json`**（PLG:437、488 原文要求）。
- 存放位置与 MCP OAuth 令牌一致：Android 用 Keystore 加密文件，桌面用只给当前用户的文件（已有实现，见 `FileMcpTokenStore` / `AndroidMcpOAuth`）。不进 rootfs、不进会话日志、不进事件。
- 替换规则：`${user_config.KEY}` 在 MCP 的 env 里替换成真值；在 skill 正文里只替换成占位符文本，不展开真值（契约草案里已标注这是「同一个函数两种语义」，实现时拆开）。

## 六、变量替换

- `${CLAUDE_PLUGIN_ROOT}`、`${CLAUDE_PLUGIN_DATA}` 等环境变量：在使用侧替换（PLG:563–578 的解析规则），不在装载时替换。装载结果里保留原始 JSON。
- `${user_config.*}`：只能出现在 MCP / LSP 的配置里与 monitors 的**非**命令处（PLG:388 原文禁止 monitors 命令引用）。

## 七、测试与变异

- 样本：`plugin-compat` 46 个，实现时逐个摘 `pendingFix`。
- 契约映射：`PluginCompatTest` 已有探针断言「还没有 `PluginLoader`」，加载器落地那天它会红，提醒摘标记。
- 变异：对每条合并规则（同名覆盖、依赖拉起、三路径规则、严格对象）各做一个变异，对应样本应变红。
- 信任：未信任的项目插件 hooks 不执行、用户层的执行——各一条端到端测试。

## 八、不做的（写清楚）

- 市场安装、第三方源（待 M5 总览待定 1）。
- LSP 服务器、monitors（待后台任务与 LSP 工具）。
- 插件的 `prompt` / `agent` / `http` 类型 hook（Min 的 hook 引擎还没有这些类型，GLM 的花费与 hook 类型那单在做）。
- `plugin eval`（M6）。

## 九、决定补充（2026-10-08，用户确认）

- **官方市场默认开**：可以浏览和安装官方源的插件。
- **第三方源不默认开**：用户手动添加时弹明确警告（说明插件可能运行命令、可能访问网络）。
- 插件的 hooks 与 MCP 服务器，无论来自哪个源，都只在所在目录被信任后启用。市场来源不改变这条规则。
