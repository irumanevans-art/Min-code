# 上下文压缩设计

> 状态：设计，2026-10-02。上位文档：`04-子系统设计.md` §4.5（压缩流水线、压缩后重挂）。
> 对标 Claude Code 的自动压缩与 `/compact [焦点]`（`research/inventory/claude-code/04-sessions-sdk-automation.md` §2），实现是自己的。

## 0. 目标

长会话迟早撞上上下文窗口。压缩要做到：

1. **原文永不删除**：日志一字不动；压缩只改变「模型看到什么」（投影），界面照样能看全文，模型需要细节时能按路径读回原文。
2. **便宜优先、缓存友好**：先**遮蔽**旧的工具输出（不花一次模型调用），攒够一批才改写一次前缀；不够再**摘要**。
   摘要请求复用当前前缀（命中缓存），只在末尾追加一条「请总结」——而不是另起一个空白请求把全文重新付一遍钱。
3. **该记住的由内核记**：改过哪些文件、任务清单、计划，由内核从日志算出来放进摘要，不靠模型回忆。
4. **可预期**：失败有熔断；撞到供应商的「上下文超长」时压缩后**只重试一次**。

## 1. 投影里的两种改写（事件）

| 事件 | 含义 | 投影效果 |
|---|---|---|
| `ToolOutputsMasked(callIds, artifacts)` | 这些调用的结果在模型视图里换成一行占位 | 结果内容 → 「[较早的 <工具> 输出已省略以节省上下文；原文在 <路径>，需要时用 Read 读取]」；`isError` 保留 |
| `ContextCompacted(id, summary, through: MessageId, trigger, instructions?, transcriptPath, tokensBefore)` | 到 `through`（含）为止的对话被一段摘要取代 | 模型视图 = `[摘要消息] + through 之后的消息`；多次压缩取最后一次（新摘要本身就覆盖了旧摘要） |

- 两个事件都**只影响 `modelMessages()`**：`history`、`toolResults` 不变，界面的转录照旧完整。
- 遮蔽的占位里给出原文路径：遮蔽前先把原文写成会话附件（`compactions/<callId>.txt`）；超过结果预算本来就落过附件的直接引用那份。
- 摘要事件的 `transcriptPath`：被摘要掉的那段对话，渲染成 Markdown 存为附件（`compactions/<id>.md`），摘要末尾告诉模型「完整原文在这里」。
- `through` 必须落在**完整的一轮边界**上：不能把带工具调用的助手消息与它的结果拆开（投影要合法：每个 tool_use 都有 tool_result）。

## 2. 什么时候压缩

**估算**：发请求前估算这次请求的输入 token。基准是上一次请求的真实用量（`lastRequestUsage`：input + cacheRead + cacheWrite，K10），
加上那之后新增内容的估算（中日韩字符按 1 token / 字、其余按 4 字符 / token，取保守）。没有基准（新会话）就整段估算。

**阈值**（按模型的 `contextWindow` 与输出预留 `maxOutputTokens`）：

```
可用 = contextWindow − maxOutputTokens − 安全余量（2%）
遮蔽线 = 可用 × 70%      → 超了先遮蔽
摘要线 = 可用 × 85%      → 遮蔽后仍超（或遮蔽腾不出 15% 的空间）就摘要
```

**遮蔽规则**（纯函数，可测）：
- 保护最近的约 40k token（按估算）——最近的工具结果模型多半还要用。
- 只遮蔽「大」的结果（> 2,000 字符）：小结果遮蔽省不了多少，却会多改写一次前缀。
- **攒批**：可遮蔽的总量不到可用窗口的 10% 就先不动，避免每轮都改写前缀（每改一次，被改位置之后的缓存全部失效）。
- 不遮蔽：被 `touched` 记为「最近一次读到的文件内容」且之后没被改过的 Read 结果？——不做这种特殊处理：占位里有路径，模型重读即可，规则简单可预期。

**手动**：`SessionRuntime.compact(instructions: String?)`（界面的 `/compact 焦点`）：空闲时直接做摘要阶段（不管阈值）。

**撞墙**：请求失败且 `kind = ContextOverflow` 时，做一次摘要后重试**一次**；还是超长就以 Failed(ContextOverflow) 结束回合（界面提示开新会话或手动压缩）。

**熔断**：同一会话连续 3 次摘要失败（模型报错、摘要为空、摘要后反而更长）就停止自动压缩，写一条 Note，直到用户手动压缩成功。

## 3. 摘要怎么生成

- **请求**：与本会话正常请求**相同的 system、tools、缓存键**，messages = 当前的模型视图 + 一条用户消息（压缩指令）。
  前缀与上一次请求相同，几乎全部命中缓存；只付指令与摘要输出的钱。指令里明确「不要调用任何工具」；模型还是调了工具就只取文字部分。
- **指令**要求固定分区（中文标题，便于下次合并）：
  1. 目标（用户要什么）
  2. 已经做出的决定与理由
  3. 当前进度与下一步
  4. 遇到的错误与教训（别再踩的坑）
  5. 用户特别强调过的要求（原话）
  加上手动压缩时用户给的焦点。「改过的文件」「任务清单」不让模型写——由内核附在摘要后面（见下）。
- **内核附加的部分**（拼在模型写的摘要后面，同一条摘要消息里）：
  - 改过的文件：从日志里 `ToolResult.touched` 与写类工具的调用算出（路径 + 最后一次改动的工具），最多 50 个，超出注明；
  - 任务清单（等任务工具合入后接上）、当前计划（计划模式里获批的计划，若有）；
  - 「完整原文在 <transcriptPath>，需要细节时用 Read 读取」。
- **用哪个模型**：本会话当前的模型（缓存共享，摘要质量也最可靠）。以后可加「用便宜模型压缩」的设置，但那样缓存不共享，未必更省。
- 摘要请求的用量计入本回合（界面的「本轮花费」能看到压缩花了多少）。

## 4. 落盘顺序与恢复

```
CompactionStarted(id, trigger)                     ← Sync：进程死在这之后，重开时知道有一次压缩没做完
写附件（被摘要掉的原文、被遮蔽的原文）
ModelRequestStarted … AssistantMessageCompleted     ← 摘要请求照常记（requestId 标为压缩）
ContextCompacted(...) 或 CompactionFailed(id, 原因)  ← Sync
```

- 摘要请求的完成事件**不进 history**（它不是对话的一部分）：用单独的 `CompactionSummarized` 记模型输出与用量，避免折叠把它当成助手消息。
- 进程死在压缩中途：重开时 `CompactionStarted` 没有配对的结束事件 → 恢复补一条 `CompactionFailed(原因 = 进程被杀)`，模型视图不变，下次请求前按阈值重新判断。

## 5. 不做（本期）

- PreCompact / PostCompact hooks：已接（2026-10-04，分支 `agent/hooks-compact`，见 hooks设计.md §8 落地情况）。
- 「空闲很久后用摘要续会话」（CC 的 resume 摘要）：等真机数据。
- 按模型族调压缩指令：先一份中文指令，评测后再分。

## 6. 测试要点

- 投影：遮蔽只改模型视图、不改 history；多次摘要取最后一次；`through` 不拆开调用与结果；遮蔽的占位里的路径能读到原文。
- 触发：估算、两条线、攒批、保护最近 40k；撞墙只重试一次；熔断。
- 缓存：摘要请求的 system / tools / 缓存键与正常请求相同（断言 `prefixFingerprint` 相等）。
- 恢复：在压缩的每个提交点之间杀进程，重开后日志合法、模型视图合法（每个 tool_use 都有结果）。
