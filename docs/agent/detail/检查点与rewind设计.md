# 检查点与 rewind 设计

> 状态：设计，2026-10-05。上位文档：`04-子系统设计.md` §4.9、`05-对标清单.md` 的 checkpoint / rewind 行。
> 事实依据：`research/inventory/checkpoints.md`（CC 官方文档；Gemini CLI、Codex、opencode、Cline 源码；JGit 在 Android 模拟器上的实测）。实现是自己的。

## 0. 一页结论

- **语义照 CC**：每条开启回合的用户消息一个检查点，建在发送前；回合中途插进来的消息没有检查点。`/rewind` 四个动作：代码和对话 / 只对话 / 只代码 / 取消；「代码」两项只在该点之后确实有改动时出现；恢复对话后原消息回填输入框。CC 的设置键 `fileCheckpointingEnabled`、环境变量 `CLAUDE_CODE_DISABLE_FILE_CHECKPOINTING`、`cleanupPeriodDays` 照认。
- **比 CC 多覆盖三样**：Bash 改的文件、子 agent 改的文件、回合之间用户或别的程序改的文件（只要在工作区里）。CC 只认 Write / Edit / NotebookEdit 的改前备份，这三样都撤不了。做法是两层（§2）：每个用户回合前对工作区拍一张**整树快照**；编辑类工具另存**改前原文**，补上快照照不到的地方并支持撤销单次编辑。
- **存储自己写**：一个按内容寻址的小仓库（SHA-256 命名、deflate 压缩、同一工作区的所有会话共用、按引用回收），不用 JGit。理由见 §3。
- **对话回退不删历史**：日志里追加一条 `conversation_rewound`，折叠时状态回到那条用户消息之前；回退掉的部分在界面里折叠显示，日志里一字不少。回退后的请求是原请求的前缀，提示缓存照常命中。
- **回滚可以反悔**：恢复代码之前先给当前状态拍一张，「撤销这次回滚」就是恢复到那一张（Cline 的事务做法）。

## 1. 什么时候建检查点

- 根会话里，**由用户发出、开启一个新回合**的输入（`InputOrigin.User`）各建一个。不建：回合中排队插入的输入（并进当前回合，与 CC 同）、子 agent 报告、hook 或后台通知带进来的输入、子会话里的委派指令。
- 建在输入落盘之后、**本回合第一个有副作用的工具执行之前**。快照与第一个模型请求**并行**：模型思考的几秒钟够快照跑完；工具执行处有一道闸——只读工具（Read / Grep / Glob 等 `readOnly` 的）不等，其余工具等快照结束（Codex 旧版 `tool_call_gate` 的思路）。
- 快照有时间预算（§3.4）。超时、失败、宿主的仓库本身出错**都不拦回合**：这个检查点记成「只有编辑记录」（退化到 CC 的能力），原因与上一次不同时给一条说明（每轮都拍不成的大目录只说一次）。回合被停下时快照也停，同样落一条「没拍完」的检查点——拍成没拍成都要有记录。
- 只有回合开头、模型回话之前提升的那条人发的消息算回退点；模型回过话之后才提升的（插话，或子 agent 报告唤醒的回合里用户插的话）不算。
- 关闭：任一层 settings 的 `fileCheckpointingEnabled: false`，或环境变量 `CLAUDE_CODE_DISABLE_FILE_CHECKPOINTING` 为真 → 两层都不做，`/rewind` 只剩「只对话」。

## 2. 两层

### 2.1 整树快照（每个用户回合）

- 范围：会话 cwd 所在的工作区根（以后有附加目录时每个根各拍一张）。
- 排除：所有 `.git/` 目录；`.gitignore`（各级）与 `.git/info/exclude` 的规则（照 git 的语义，§3.3）；不是 git 仓库时用一张默认排除表（`node_modules`、`.venv`、`venv`、`__pycache__`、`.gradle`、`build`、`dist`、`target`、`.cache`、`.pytest_cache`、`.mypy_cache`、`.tox`，与 Codex 旧版、Cline 旧版的表取交集再加 JVM 系）；单文件超过 4 MiB 不存内容。
- 被排除、被跳过的路径**记进快照**（排除的记目录前缀，跳过的记路径与原因）。这是回滚安全的关键：回滚只碰「目标快照与当前扫描都看得见」的路径，看不见的一律不动——绝不能因为某个大文件没存，回滚时就把它当成「当时不存在」删掉。
- 符号链接记进快照（用于显示差异），回滚时跳过并计数（CC 2.1.216 起同样跳过）；硬链接无法在 Android 上可靠识别，不特殊处理。可执行位记录并恢复。目录集合也记：回滚后变空、且目标快照里没有的目录删掉（CC 不处理目录，这里多做一点）。
- 子 agent 不单独拍：它们与父会话共用工作区，改动落在父会话下一次检查点之前，自然被覆盖。

### 2.2 编辑记录（每次编辑类工具调用）

- Edit / Write / NotebookEdit 写盘**之前**，经 `ToolContext` 上的新端口把改前原文存进同一个仓库，拿到内容 id；写盘之后把改后内容也存一份。`FileEdit` 增加两个可选字段 `before` / `after`（内容 id；文件原来不存在时 `before` 为 null）。旧日志没有这两个字段，照常读。
- 用途：①撤销单次编辑（产品侧「改动的文件」面板的撤销按钮，子 agent 的编辑也能撤——产品 2.1.31 那版对 CC 引擎做不到）；②整树快照照不到的文件（工作区外、被 `.gitignore` 排除的 `.env`、超过 4 MiB 的）；③快照超时或关掉整树快照时的退路；④冲突检测：回滚时文件当前内容不等于 `after`，说明之后又被别人改过（§4.3）。
- 每个文件在本会话里的**第一份**改前原文一直保留（CC 同：它是「本会话改了什么」的基线）。

## 3. 存储

### 3.1 为什么不用 JGit

调研实测 JGit 7.8 在 Android 15 模拟器上能跑，但：它的字节码引用了 API 30–34 才有的 JDK 方法，还有 Android 根本没有的 `ProcessHandle` 与 JMX，API 26–33 的真机上会不会 `NoSuchMethodError` 没法验证（Min 的 minSdk 是 26），要为整个 App 打开 core-library desugaring；jar 3.4 MB；它的 `add` 不能按预算中途停。而这里只用到三件事：拍快照、比两张快照、按快照恢复——没有分支、合并、历史遍历。自己写一个内容寻址的小仓库，预计 1000 行上下，桌面与 Android 同一份代码、行为一致，排除规则、预算、回收都在自己手里。代价是 `.gitignore` 的匹配要自己写——用本机真 git 的 `git check-ignore` 生成兼容样本来钉住（§6）。

### 3.2 布局

一个工作区一个仓库，所有会话共用（同一工作区的第二个会话不用再存一遍全量）：

```
<存储根>/snapshots/<工作区键>/
  objects/ab/cdef…           内容，deflate 压缩；文件名是原文的 SHA-256
  manifests/…                快照清单，本身也按内容寻址（同一份清单不重复存）
  index                      统计缓存：路径 → 大小、mtime、内容 id（只为加速，丢了可重建）
  refs/<会话 id>/<检查点 id>   回收的根：指向清单或内容
  lock                       回收时的排他锁
```

- 存储根：Android 是 App 私有目录 `filesDir/agent/`（与会话日志同级，**不在 rootfs 里**：agent 的 Bash 碰不到它，改不了自己的退路）；桌面 CLI 是 `~/.min-agent/`（与 `sessions/` 同级）。
- 工作区键：工作区根 guest 路径规范化后的 SHA-256 前 16 位，再加最后一段目录名方便人看。
- 清单内容：按路径排序的条目（路径、类型 file / symlink / dir、可执行位、大小、内容 id）+ 排除的目录前缀 + 跳过的路径与原因 + 扫描时间。

### 3.3 扫描、增量与「刚改过」

- 每次快照全量 stat 一遍工作区（宿主侧直接走文件系统，不经 proot：调研 §3.2，元数据密集的操作在 proot 里慢 26–50 倍）；`index` 里大小与 mtime 都没变的文件不重新读，直接沿用内容 id。
- **刚改过的文件要重新读**：Android 模拟器上测到的文件时间戳精度是 2 秒，同一秒里先被哈希、又被改了而大小不变的文件，单看 mtime 会漏。照 git 的「racily clean」做法：mtime 不早于上一次写 `index` 时间的条目，下次一律重新哈希。
- `.gitignore` 语义照 git 文档：取反、只匹配目录的尾 `/`、以 `/` 锚定、`**`、字符类、反斜杠转义、下层 `.gitignore` 覆盖上层、父目录被排除时子路径不能被取反救回。全局 excludes（`core.excludesFile`）不读——它在用户的 git 配置里，proot 里通常没有。
- 写内容：先写临时文件再改名（对象不可变，并发写同一个对象无害）。对象不 fsync（进程被杀不丢页缓存里的数据，只有断电会丢；丢了的对象在恢复时报「备份缺失」，与 CC 的报错同义），清单写完 fsync，然后才落 `checkpoint_taken`。

### 3.4 预算与退化

| | 桌面 | Android |
|---|---|---|
| 增量快照（常态） | 10 秒 | 15 秒 |
| 工作区的第一次快照 | 60 秒 | 60 秒 |
| 文件数上限 | 50,000 | 20,000 |
| 一次快照新增内容上限 | 512 MiB | 256 MiB |

- 超时、超上限：这次快照作废（不留半张——半张快照会让回滚误判），检查点记 `unavailable` 并写原因；工作区第一次快照就超限的，记在仓库里，之后的会话直接跳过整树快照，只用编辑记录，并在会话开头说一次（「这个目录太大，回滚只覆盖编辑工具改的文件」）。设置里能重试。
- 快照可取消：回合被用户停掉时一起停。

### 3.5 回收

- 根：每个会话最近 100 个检查点的清单（CC 同数）、本会话每个文件的第一份改前原文、所有「回滚前」快照（§4.2）。
- 过期：会话最后一次存东西后超过 `cleanupPeriodDays`（默认 30 天）整个会话的根删除；删会话时立即删。过期后 `/rewind` 仍列出旧检查点，恢复代码时报「备份已清理」（CC 同）。
- 回收是标记-清除：持排他锁，从所有根标记，删掉没被标记、且**修改时间早于 1 小时**的对象（给正在写的快照留余地，git 的 prune 也这样）。最多一天一次，在会话关闭或 App 空闲时做。
- 设置页显示占用并能清空某个工作区的仓库（清空 = 删所有根后回收）。

## 4. rewind

### 4.1 入口与列表

- CLI：`/rewind`（别名 `/checkpoint`、`/undo`，与 CC 同），列出本会话的检查点（序号、时间、消息开头、该点之后的改动统计）。App：会话里长按一条用户消息「回到这里」，加上会话菜单里的「回退」列表（手机上没有 Esc Esc）。
- 每个检查点显示「从这里到现在」改了哪些文件（当前工作区对这张快照的差异）。差异为空时只给「回退对话」。
- 内核的入口是 `SessionRuntime.previewRewind / rewind / undoRestore / restoreCalls`（2026-10-05 落地）；界面接入（M2-B B7）时再包成引擎无关的 `SessionCommand.Rewind(…)`。预览返回要恢复 / 删除 / 跳过的文件、撤不回的文件、外部改过的文件、两种范围各会停掉哪些子 agent——界面的确认框照它写。
- 回退与恢复是会话空闲时的「维护」：不占回合的位置（停止键停的是回合，停不断做到一半的恢复），与回合互斥；期间到的输入进收件箱，做完了接着开回合。

### 4.2 恢复代码

1. 会话必须空闲（没有回合在跑）；**先停掉本会话所有在跑的子 agent**（它们可能正在写文件，会把刚恢复的内容又改回去），再动文件。同目录下别的根会话在跑时确认框点名（界面接入时做）。
2. **先拍一张「回滚前」快照**（同 §3 的算法，作为一次性的反悔点）。
3. 算差异：目标快照 vs 回滚前快照；只处理两边都看得见的路径（§2.1）。目标里有、现在没有或不同的 → 写回目标内容（恢复可执行位）；现在有、目标里明确没有的 → 删除；回滚后变空、目标里没有的目录 → 删除。
4. 快照照不到的文件用编辑记录补：该检查点之后的编辑类调用，按时间倒序把文件还原到它们的 `before`（原来不存在的删除）。
5. 写之前逐级确认父目录都是真目录、不是符号链接，不往工作区外写（CC 2.1.216 修过同类问题）。
6. 恢复一旦开始就做完并落盘（不可取消）：停在半路会留下改了一半、日志里又没有记录的工作区。落 `files_restored`（Sync）：目标、回滚前快照 id、恢复 / 删除 / 跳过（带原因）的路径。部分失败照常落盘，界面给「恢复了 N 个，跳过 M 个」并能展开看是哪几个、为什么（CC 只给个数，路径藏在调试日志里）。
7. **告诉模型**：只恢复代码、保留对话时，模型的对话里还留着它改文件的记录，它会以为文件还是改过的样子。所以下一条用户消息前加一段 system-reminder：「用户把工作区回滚到了第 N 轮之前：恢复了 …，删除了 …。之前读过的这些文件内容已过时，需要时重新读。」Edit 之前必须重读不用另做：「先读后改」比对的是上次看到时的大小与 mtime，恢复写盘必然改 mtime，旧的读取记录自然对不上（删掉的文件 stat 不到，同样过不了）。CC 2.1.260 修过 rewind 后读文件记录残留的问题，这里由现有机制保证。
8. 「撤销这次回滚」：以「回滚前」快照为目标再做一次恢复代码。它只覆盖快照照得到的文件：第 4 步用编辑记录补回去的（工作区外、被排除的、超过单文件上限的）撤不回，确认框里要说。

### 4.3 外部改动与冲突

- 回滚会覆盖检查点之后**所有**的改动，包括用户手改的——这正是「回到那时候」的意思，也是 Bash 能被覆盖的原因。但确认框要把「不是 agent 改的」单独列出来：某个文件的当前内容既不等于该会话最后一次编辑的 `after`、也不等于最近一次检查点里的内容，就算外部改动。
- 因为第 2 步有「回滚前」快照，覆盖掉的外部改动也能找回来。

### 4.4 回退对话

- 落 `conversation_rewound { toMessageId }`（Sync）。折叠规则：**对话范围的状态**回到那条用户消息落盘之前——历史、工具结果、hook 上下文、按需加载的记忆、任务清单、遮蔽与压缩视图（目标点在某次压缩之前时，压缩也一并回退）；**会话范围的设置**不回退——模型、effort、权限模式（含计划模式：日志里分不清模式是人切的还是工具切的，一律保持现状）、会话规则、hooks / MCP / skills 的快照、用量、任务编号（不复用）。区分原则：模型在对话里看见并据此行动的，回退；用户在会话外调的开关，不回退。实现见 `agent/kernel/.../CheckpointState.kt` 的 `ConversationScope`。
- 「最近一次看到」由工具结果推出（`SessionState.lastSeen`），回退掉的工具结果一起消失，读文件记录自然回到那时候，不用另外清。
- 那条用户消息的原文与附件回填输入框。
- 在那之后起的**子 agent** 一律安静地停掉，确认框里列出。它们在折叠里被标成「已回退」：之后再送来的报告不进收件箱、续聊找不到它们，回退那一刻已在收件箱里的报告一并清掉——由折叠保证，与报告什么时候送到无关。之后起的**后台命令**暂不处理：内核没有后台命令的登记表（句柄只在给模型的文字里），见 §7。
- 回退掉的消息在界面上折叠成「已回退的 N 条消息」，能展开看，不能再继续——要「另走一条路」用分支（以后的 `/branch`，复制日志成新会话，CC 同）。不做 redo：回退之后又发了新消息，「前进」就没有意义了；没发之前想反悔，再回退到更晚的检查点即可，因为回退不删任何东西。
- 「两者」= 先恢复代码再回退对话，界面上是一个动作、日志里是两条事件。

### 4.5 提示缓存

回退后的历史是原历史的前缀：工具表、系统提示不变，前缀里此前写过的缓存条目只要没过期就照常命中。会破坏前缀的只有两种情况：回退的同时改了会进提示的东西（§4.2 第 7 步的提醒加在**下一条**用户消息上，不改已有消息）；目标点在压缩之前（回到未压缩的原始历史，下一个请求会更长，可能紧接着触发一次自动压缩——这是用户选的，确认框提示一句）。

## 5. 事件与格式

- `checkpoint_taken { checkpointId, turnId, messageId, root, manifest?, status: complete | unavailable, reason?, stats { files, bytes, newBytes, skipped, durationMs } }`
- `FileEdit` 增加可选的 `before`、`after`（内容 id）。
- `files_restored { restoreId, target: checkpoint | calls, preRestore, restored[], deleted[], skipped[{ path, reason }] }`
- `conversation_rewound { rewindId, toMessageId }`
- 全部登记 `agent/store/FORMAT.md`；旧日志缺字段照常读。内容不进日志，日志里只有内容 id。

## 6. 端口与分工

**spi**（新端口，`HostPorts` 上有默认值「不可用」，测试替身不受影响）：

```kotlin
interface WorkspaceSnapshots {
    suspend fun snapshot(root: GuestPath, budget: SnapshotBudget): SnapshotResult      // 清单 id + 统计，或 Unavailable(原因)
    suspend fun preserve(content: ByteArray): ContentId                                // 编辑记录：存一份内容
    suspend fun diff(from: ManifestId, to: ManifestId?): List<PathChange>              // to = null：对当前工作区现扫
    suspend fun restore(root: GuestPath, target: ManifestId, extra: List<FileRestore>): RestoreResult
    suspend fun retain(sessionId: SessionId, roots: Set<StoreRef>)                     // 回收的根
    object Unavailable : WorkspaceSnapshots
}
```

`ToolContext` 增加 `preserve`（有默认值：不存，`before` / `after` 为 null）。

## 7. 已知限制（先写下来）

- 工作区外被 Bash 改的文件（例如 `~/.bashrc`）不覆盖；工作区外被编辑工具改的有编辑记录。
- 被 `.gitignore` 排除、又被 Bash 改了的文件不覆盖（编辑工具改的有记录）。
- 第一次快照要把工作区里没被排除的文件全存一遍（压缩后，源码通常是原大小的三分之一上下）；设置页能看到占用、能清。
- 真机的耗时只能等 R1 在真机上测；表里的预算是按模拟器数字和调研里 JGit 的量级定的，测完再调。
- 回退对话不停后台命令：它们照常跑，界面的后台任务列表里仍能看到、能停；模型在回退后的对话里不知道它们。要停得先让内核登记后台命令（与 Monitor / 后台任务那一期一起做）。
- 子会话工作区外的编辑记录不随父会话的「恢复代码」还原（父会话只看自己的编辑记录与整树快照）；子会话自己的「改动的文件」面板能撤。
- 宿主没有仓库时，Write 仍会为编辑记录把 2–16 MiB 的原文读进内存（存不下就丢）：这种大文件的整体覆盖很少见，先不为它在工具上加一个「能不能存」的开关。
