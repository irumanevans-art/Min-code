# agent 团队与邮箱设计

日期：2026-10-08。状态：草案。依据：CC 的 agent teams（`D:\kimi\workspace\research\inventory\claude-code\` 下的 agent 相关调研，以及 `raw\mcp\cc-sub-agents.md`）；Min 现有的子 agent（`docs/agent/detail/子agent设计.md`）。待定项：并发上限（M5 总览待定 2，本设计先按建议值 3）。

## 一、要解决什么

现在 Min 的子 agent 是「父派子、子交报告、结束」。团队要的是：多个成员**同时**存在、**互相发消息**、**共享一份任务清单**，由一个负责人协调。这是 05 清单里「agent teams（共享任务清单、邮箱）」与「cross-session messaging」两行。

## 二、核心决定

1. **成员 = 子会话**。每个团队成员就是一个子会话（复用 `SessionHub` 的子 agent 机制：独立日志、独立回合、父会话收报告）。不另起一套执行体。
2. **邮箱 = 日志里的事件**，不是内存队列。发消息写一条事件到收件人会话的日志；收件人在下一回合开始前读取未读消息（和现有 `SendMessage` 的 inbox 同一条路径）。这样重开会话、崩溃恢复、日志即真相都不用特殊处理。
3. **任务清单 = 从日志折叠出来的状态**。新增事件 `team_task_*`（创建、认领、完成、更新），团队的任务表由团队根会话的日志折叠得到。成员只能改自己认领的任务，负责人能改全部。
4. **权限不绕过**。成员的工具调用审批仍然挂在根会话的 hub 树上，由用户在界面上答（与现有子 agent 审批一致，见 `ConsoleUi` 对整棵树的处理）。团队不给成员额外权限。
5. **并发上限**：默认同时运行的成员最多 3 个（待定 2 的建议值），超了排队。上限是设置项，不写死。

## 三、事件（新增，需登记 FORMAT.md）

| 事件 | 含义 | 关键字段 |
|---|---|---|
| `team_created` | 建团队 | 团队 id、负责人会话、成员规格（名字、类型、提示词） |
| `team_member_joined` | 成员加入（子会话建好） | 团队 id、成员名、子会话 id |
| `team_message` | 成员之间的消息 | 发件人、收件人（或「全体」）、正文或附件引用 |
| `team_task_created` / `team_task_claimed` / `team_task_done` | 任务清单变化 | 任务 id、标题、认领人、状态 |
| `team_disbanded` | 解散 | 原因（完成 / 用户结束 / 出错） |

所有事件都是 append-only。折叠函数是纯函数。

## 四、与现有机制的关系

- **SendMessage / ListAgents**（05 清单里的一等邮箱）：团队的 `team_message` 是它的底层。单独的子 agent 也用同一条路，不再分两套。
- **子 agent 的报告**：成员完成回合后，报告照常交给**负责人**（不是父会话）。负责人决定要不要转给用户。
- **检查点与回退**：团队成员的文件改动进检查点树（和子 agent 一样）。回退根会话时，成员要先停（沿用现有「先停子 agent」的规则）。
- **分身（fork）**：成员不能再开团队（防止无限嵌套）。团队深度上限沿用 `HubLimits.maxDepth`。

## 五、界面（B7b 之后再做，本期只保证内核面）

- 团队页：成员列表（状态、当前任务）、任务清单、消息流。
- 成员的审批卡挂在根会话的抽屉里，标明是哪个成员。
- 本期内核有 `SessionHub.summaries()` 与 `pending`（hub 里的待处理项）就够界面读。

## 六、测试

- 折叠：任务清单的每种状态转换、非法转换（成员改别人的任务）被拒。
- 邮箱：消息写入收件人日志；收件人下一回合读到；重开会话后仍读到且只读一次。
- 并发上限：超过 3 个时第四个排队，前一个结束后才开始。
- 日志即真相：每个团队测试结尾做 `fold(log) == 运行时状态`。
- 权限：成员的写工具调用出审批卡，审批结果回到成员（不是负责人替它批）。
- 变异：并发上限去掉、邮箱改成内存队列、成员能改别人的任务——各一个变异，对应测试应变红。

## 七、不做的

- 成员跨机器协作（Min 只在一台手机上）。
- 成员直接访问彼此的日志（只通过邮箱）。
- 团队自动扩员（负责人只能用预先声明的规格建成员）。
